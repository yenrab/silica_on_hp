# Silica on the HP EliteDesk 705 G5 SFF without an operating system

Ideation record, 2026-11-21. Nothing has been built yet.

Goal: run a Silica app (`../silica`) on the HP with no OS installed, the way apps run on the
ESP32-S3 raw target.

## Decisions (Lee, 2026-11-21)

1. **Boot as a UEFI application directly.** No third-party bootloader (Limine was the alternative
   considered: less work, starts all cores for you, but puts someone else's code in the boot path).
2. **Hardware first.** Bring-up happens on the HP itself, not in QEMU + OVMF. Same choice as the
   ESP32-S3 port.
3. **`nix` can go offline.** The HP was the `nix.local` Linux x86-64 build machine; it may stop
   serving that role.
4. **No OS on the machine at all.** Linux is wiped from the HP as part of the experiment. The box
   is a raw target only. (This supersedes any plan that keeps Ubuntu on the disk.)
5. **First app (2026-11-22).** The Mac sends a message over TCP and the machine replies with the
   number 42. The TCP stack, its supporting code (Ethernet driver, ARP, IPv4) and threading are to
   be written in Silica.
6. **Memory (2026-11-22).** The run claims all the RAM the machine has, since only one app runs at
   a time. In practice: every range the firmware's memory map marks usable once firmware boot
   services are given up. Ranges the firmware keeps (its runtime services, ACPI tables, reserved
   and device ranges, memory set aside for the integrated graphics) are not available.
7. **Actor stacks (2026-11-22).** Actor stacks remain growable as the language specifies
   (specification section 15.1.2.2: a contiguous reservation made at spawn with no access, memory
   committed on fault in chunks that double from one page to 1 MB, the five release algorithms, a
   stack policy on every spawn). This is the language's contract, not an ESP32-S3 feature, and the
   raw x86-64 runtime implements it as designed. Consequences: a page-fault handler and the
   runtime's own page tables are needed as soon as actors exist; stack memory is committed in
   4 KB pages from a physical-page allocator; the default reservation ("physical memory plus
   swap") is the machine's usable RAM, with no swap; `:release_when_idle` needs the clock.
8. **Interrupts (2026-11-22).** Placement: the timer interrupt at ladder rung 4, the Ethernet
   chip's interrupt at rung 8. Model: the scheduler never masks interrupts, because handlers touch
   nothing it owns; a handler sets a pending flag and the scheduler turns it into a message for
   the owning device actor at the next dispatch boundary; the handler acknowledges generically by
   masking the vector, and the Silica driver does the chip-specific work and unmasks. Detail in
   `DEVELOPMENT_LADDER.md`. (Lee accepted "1.c, 2.b"; question 2 had two parts, delivery and
   acknowledgement, and option B was taken for both.)
   Also decided: the page-fault path and the context switch run with interrupts masked (two
   short assembly paths; the Silica scheduler still needs no masked sections); a device actor
   receives a bare `:interrupt` message; ownership is checked twice, by a board-pack table keyed
   by PCI vendor and device ID and by a run-time claim that the runtime refuses to grant twice.
9. **Emit target (2026-11-22).** A general target, `x86_64_uefi_raw`, with a board pack for this
   machine under it (`board/hp_elitedesk_705_g5/`). It starts as a copy of `emitter/linux_x86_64`
   and diverges, as the other ports began; the Linux target is left untouched.
10. **Image production (2026-11-22).** The cross compiler emits for the EFI object format
    directly: the `x86_64_uefi_raw` emitter writes COFF-clean assembly, clang on the Mac assembles
    it, and `lld-link` links the EFI application. Not ELF converted afterwards, and not a
    hand-written EFI header.
11. **C library dependence (2026-11-22).** The copied emitter's calls to the C library (about 50
    functions) are all rewritten up front to call the raw runtime's own entry points. No C-named
    function remains and no stand-in C library is built. (Option B of three; the alternatives
    were a stand-in C library, and a split that kept helper and heap names and replaced
    operating-system services rung by rung, which I had recommended.)
12. **Runtime contract (2026-11-22).** Low level: the copied emitter keeps its embedded assembly
    runtime, and each C library call in it is replaced by a primitive. Designed fresh for this
    target; the ESP32-S3 runtime's entry points are not reused. (I had recommended a two-level
    contract with ESP32 names revised.) Consequence recorded with it: decision 5's "threading in
    Silica" is read as the thread layer under the embedded actor runtime, since the actor
    scheduler itself stays as embedded assembly. That reading is mine and awaits confirmation.
13. **Multi-core (2026-11-22).** More than one core is designed in from the beginning: per-core
    data, primitives safe with other cores running, core identity in the contract, start-up split
    into "first core" and "every core". The first app still runs on one core and the other cores
    are not started on the ladder.
14. **Order revised to avoid building things twice (2026-11-22).** The polled clock moves to
    rung 2, ahead of actors; the Ethernet driver is written once in a wake-driven shape, woken by
    a timer message on rung 6 and by the chip's interrupt from rung 8; the Secure Boot route is
    decided before the one keyboard-and-screen session.

## Proposed shape

A new raw emit target, `x86_64_uefi_raw` (name decided 2026-11-22), built from two existing halves:

- **Instruction selection** from `compiler/src/emitter/linux_x86_64`. It already leaves the red zone
  unused and never moves `rsp` inside a body, which is what interrupt-safe bare-metal code needs.
- **Board pack and runtime** shaped like `compiler/src/emitter/ESP32-S3_raw/board/runtime/rt_*.S`
  (start, vectors, console, heap, actors, device, ...), rewritten for x86-64.

Boot: the image is an EFI application (PE/COFF) that the firmware fetches over the network from the
Mac (see the headless section). The firmware hands over the CPU in 64-bit mode with a memory map, the ACPI tables and a framebuffer. The
runtime calls `ExitBootServices` and owns the machine from there. Secure Boot must be off. Calls into the firmware use the Microsoft x64 calling convention,
not SysV.

## Stages

**Superseded on 2026-11-22 by `DEVELOPMENT_LADDER.md`.** The list below is the first sketch, kept
as a record of the discussion.

1. **Hello.** UEFI app, one core, console sent through the firmware's network driver (no display
   is attached), bump heap from the UEFI memory map, `main` runs and resets.
2. **Faults.** IDT, so a fault prints the status-70 banner. Own page tables give real guard pages
   under growable actor stacks.
3. **Time.** Calibrate the TSC, then the local APIC timer. Could be the timer-IRQ clock the ESP32
   port still lacks.
4. **Cores.** Read the ACPI MADT, start the other seven threads (INIT-SIPI-SIPI with a real-mode
   trampoline), each with a cooperative scheduler like the two LX7 cores.
5. **Devices.** PCI enumeration, then the RTL8168. With no display and no OS this driver is also
   the console once firmware services are given up, so it may need to move ahead of stages 2-4. It
   is also what lets the `transit_*_tcp` examples have somewhere to go. Those need a TCP/IP stack: in Silica, or C through Fifi.
6. **Storage and beyond.** NVMe. With 16 GB of RAM this is the first raw target that could
   eventually host the compiler itself.

## Differences from the ESP32-S3 port

- **Devices are discovered at run time.** The ESP32 board pack has a compile-time window table; PCI
  device addresses are known only after enumeration. `map_device` checking needs a dynamic story.
- **Port I/O exists.** `peek` / `poke` are 32-bit MMIO only today. A PC needs 8/16/64-bit widths and
  probably `in` / `out` for legacy devices.
- **`mem(Space)` can be exact.** x86 page attributes (PAT) give real uncached and write-combining
  memory, much like MAIR on AArch64.
- **No glibc.** Everything the hosted runtime gets from Linux (signals, threads, `mmap`, clock) has
  to be replaced. Fifi C code must be freestanding.
- **Not quite nothing underneath.** Firmware SMM and the AMD PSP keep running, as the ROM does on
  the ESP32.

## How the ESP32-S3 grows stacks without an MMU, and what that means here (2026-11-22)

Read from `ESP32-S3_raw/board/README.md` ("Stack budget") and the project notes on items D and F.

- Each actor has two stacks, a machine stack and an auxiliary stack. Each is a **chain of heap
  chunks**, not one contiguous range. An actor holds none until its first dispatch (2 KB machine,
  512 B auxiliary).
- **Growth is by checks the compiler emits, not by faults.** Every function prologue compares the
  new stack pointer with the current chunk's limit; every auxiliary reservation does the same.
  Below the limit, the runtime allocates the next chunk (double the last, up to 16 KB / 4 KB, or
  as big as the frame needs) and the frame moves there. Returning from a frame that entered a
  chunk goes through a runtime routine that makes the chunk below current again.
- Release happens at the message boundary under the actor's `stack_policy` algorithm; a lowered
  reservation caps the chain (`:stack_exhausted`); heap exhaustion is abort 71.
- Each chunk ends in a 64-byte guard band watched by a hardware data breakpoint.
- `main` is not an actor: its stacks are fixed, sized per image by a static walk of the linked
  code, and never grow.

Meaning for the HP:

- That mechanism lives in the Xtensa emitter (limit checks in every prologue, frames that hop
  chunks, the return routine). The x86-64 emitter has none of it: it assumes one contiguous stack
  and relies on the fault-driven design of specification section 15.1.2.2. Adding the ESP32
  mechanism to the x86-64 emitter only to run actors as a firmware guest would be work that is
  thrown away once the image leaves the firmware.
- So on the HP, actors use the specified fault-driven design, and **actors start only after the
  image has its own page tables and fault handler**, which means after it leaves the firmware.
- `main` needs no growth, so the language ladder (no actors) can still run as a firmware guest.
- Consequence: paging, faults and the first actors are brought up with no firmware console and
  before any Silica network driver exists (a Silica driver is a device actor). The bootstrap
  console for that stretch is the hand-written transmit-only Realtek routine from pre-development
  test image 7, called from the runtime. It is temporary and is replaced by the Silica stack.

The ladder that follows from this is in `DEVELOPMENT_LADDER.md`.

## Headless operation with no OS on the machine (revised 2026-11-21)

Two facts shape the loop:

- Lee has **no keyboard and no monitor** for the HP.
- **Linux has been wiped.** The NVMe SSD is blank, the machine has no operating system at all, and
  it is no longer the `nix.local` build host. (Decision 4 above.)

An earlier draft of this section used Ubuntu on the NVMe as the "programmer" (copy the image to the
EFI partition, set a one-shot next boot, reboot, come back to Ubuntu to read results). That loop no
longer exists. It is recorded here only so it is not proposed again.

The loop now works like a board on a cable, with the Ethernet cable as the only channel:

1. **Load: network boot from the Mac.** The firmware's IPv4 network boot entry already exists
   (`Boot0001`, Realtek NIC, MAC `e8:d8:d1:c5:92:fd`). With a blank disk and no USB stick, it is the
   first boot entry that can succeed. The Mac answers the boot request and serves the EFI image
   (a boot-request responder plus a file server on the Mac; details to design). This is the
   equivalent of flashing, and nothing is ever stored on the HP.
2. **Run.** The firmware starts the Silica image straight from the network.
3. **Read output.**
   - While firmware boot services are alive (before `ExitBootServices`), the image can send
     packets through the firmware's own network driver. No Silica driver is needed. This is the
     analogue of using the ESP32 ROM's print routines, and it is the console for the first stages.
   - After `ExitBootServices`, the console needs the Silica RTL8168 driver: a UDP console to the
     Mac, the real equivalent of the board's UART. This moves the NIC driver earlier in the stage
     order than first planned.
   - A short status can also be left in a UEFI variable through firmware runtime services, but
     with no OS on the box there is nothing to read it back except the next raw image.
4. **Reset.** The image calls the firmware's reset service; the firmware network-boots again and
   picks up whatever image the Mac is serving now.
5. **Hang recovery.** Before `ExitBootServices` the firmware watchdog can reset a hung image.
   After it, the chipset's hardware watchdog can be armed (present by device ID, untested). The
   fallbacks are the power button, or a switched outlet with the firmware set to power on when AC
   returns (`AfterPowerLoss`). Wake-on-LAN was disabled in the firmware's wake table when read.

Other channels considered:

- **Internal speaker beeps** for the first sign of life (the eBadge buzzer's role). The firmware
  declares a speaker device; whether one is fitted is not confirmed.
- **Serial port** (HP option card or a PCIe serial card): discussed and **set aside by Lee on
  2026-11-21** as not realistic, because the image has to be loaded over the network anyway, so
  serial would be a second cable and extra hardware beside a channel that is already required.
  The network is the one channel. The gap serial would have covered (output after firmware
  services are given up, before a full network driver exists) is to be closed with a minimal
  transmit-only, polled Realtek driver, and possibly a log kept in RAM that the next boot sends
  out through the firmware's network driver (survival of RAM across a reset is untested).
- **USB stick** carrying `BOOTX64.EFI`: works for loading, but output still needs the network, and
  it means walking to the machine for every run.
- **USB 3 debug cable** (xHCI debug capability): nothing on the Mac side supports it out of the
  box. Set aside.

### What the documents assume was done before the wipe

These are written as done. Each needed either Linux on the box or a borrowed keyboard and display,
so each is hard to do afterwards:

- **Secure Boot is off.** It was enabled when read on 2026-11-21, and an unsigned image is refused
  while it is on, over the network as well as from disk. Turning it off is done in firmware setup
  and asks for a code shown on screen to be typed back: keyboard and display required.
- **Network boot works and is reached without a key press** (boot order, and any HP "network boot"
  setting).
- **Power-on after AC loss is enabled**, if a switched outlet is to be the reset of last resort.
- **Root-only hardware details were captured** (memory modules, ACPI tables, firmware memory map,
  PCI capabilities). They were *not* captured in the 2026-11-21 session; `HARDWARE.md` section 11
  lists them and how the raw image can read them itself instead.

If any of these turns out not to have been done, the recovery is a borrowed USB keyboard and any
HDMI or DisplayPort screen for the firmware settings, or a live Linux USB stick for the captures.

With Secure Boot off and the image fetched by network boot, nothing authenticates the image. The

## Consequences of having no OS on the machine

- There is no native Linux x86-64 machine any more: no `linux_x86_64` fixed point, no native trial
  runs, and no place to run or debug x86-64 Silica code under an OS before it goes raw. The Mac's
  cross compiler (`binaries/silica-compiler-linux_x86_64`) still emits x86-64 assembly.
- `.silica_build_hosts` in the Silica checkout still names `nix`; that row is dead and the
  multi-platform build scripts will fail on it until it is removed or pointed at another machine.
- `ssh lee@nix.local` no longer answers. Nothing can be inspected on the HP except by a raw image.
- The raw image is assembled and linked on the Mac, so the Mac needs an x86-64 assembler and a
  linker that can produce a PE/COFF EFI image.
